## 一、结论速览

| 诉求 | Codex 对应能力 | DSH 官方现状 | 本插件落点 |
|---|---|---|---|
| ① 已发出消息 → 添加到新对话 | 消息级 "Branch in new chat"、`/fork` | `session/fork` RPC **已存在**，但 UI 只挂在**助手**尾部（`turnTail`），用户消息没有入口 | 用户消息 hover → ⑂ 按钮，按 Turn 精确定位边界 |
| ② 已发出消息 → 侧边栏提问 | `⌘⌥S` / `/side` 侧聊 | `sidebarRight` + `sidebarRightTabs` **已存在**，但没有任何内置"就某条消息提问"的 tab | 用户消息 hover → ▯ 按钮，注册 `codex-parity-ask` tab |
| ③ 刚发出消息 → 编辑重发 | hover Edit 按钮、`Esc Esc` | **完全没有**。`conversation.chat.node` 的 user 渲染器不传 `onBranch`，也无 `extraActions` | 仅最新一条用户消息 → ✎ 按钮，分叉式重发 |
| ④ 左侧会话列表 → 右键删除 | 右键 Rename / Pin / Archive | **没有任何删除 RPC**。`⋮` 菜单只有 置顶/重命名/分叉/归档 | 行右键菜单 + `⋮` 菜单项，归档 + 回收站 |

**核心事实**：DSH 的 slot 与 RPC 体系已经具备实现这四项功能所需的**全部原语**，缺的只是接线。生态里 20+ 个仓库在重复实现同一件事（会话删除），正是因为这一层接线官方没做。

## 三、源码取证：DSH 到底给了什么

### 3.1 官方 slot 面

客户端 slot 分四种 kind：`single` / `list` / `keyed` / `chain`。与本次相关的：

| slot | kind | 提供方 | 用途 |
|---|---|---|---|
| `sidebar.workspaces.session.menu.item` | list | ui-workspace | 会话行 ⋯ 菜单项（官方占用 order 100/200/300/400） |
| `sidebar.workspaces.session.row.action` | list | ui-workspace | 行内 hover 按钮 |
| `conversation.chat.node` | **keyed** | ui-chat | 按节点 kind 分派渲染器 |
| `conversation.chat.turnTail` | list | ui-chat | 轮次尾部动作区 |
| `sidebar.right.pane.tab[.title]` | keyed | ui-sidebar-right | 右侧栏 tab 正文/标题 |
| `shell.overlay` | list | shell | 全局弹层 |
| `settings.section` | list | ui-settings | 设置页分节 |

**关键约束（`dsh-client-ui-slots` 源码）**：

```js
case "keyed": {
  const occupant = rec.entries.find(e => e.options.key === options.key && (e.options.priority ?? 0) === priority)
  if (occupant) throw new Error(`keyed slot "${options.name}" already has an entry for key "${options.key}" ...`)
}
```

同 key **同 priority** 的第二次注册**直接抛错**。`ui-chat` 已在 `conversation.chat.node` 的 `user` cell 上注册，所以在同 key 叠加**不可能**；只能换 priority 遮蔽（SpookySandwich 的做法）。

### 3.2 官方 RPC 面

从 `dsh-api-session-controller` / `dsh-api-workspace-controller` 取证：

**存在**：`session/fork`（`{sessionId, atSeq?}`）、`session/create`、`session/prompt`、`session/rename`、`workspace/archiveSession`、`workspace/unarchiveSession`、`pin/unpin`

**不存在**：`session/delete`（全量枚举确认）

`session/fork` 的语义（`lib/index.js:776`）：

> 从一段精确的事件前缀创建新 Session。`atSeq` 是**闭区间切点**；省略时取最后一个已完成轮次。开放的切点会补上合成 closer。

边界校验：
```js
if (boundary === void 0 || source.events[boundary]?.seq !== boundary)
  throw new RemoteError("session/fork-unavailable", ...)
```

所以 `atSeq` 必须是日志里**真实存在**的 seq。这让"用 Turn 身份在 host 侧反查边界"成为最稳的客户端协议。

### 3.3 会话存储

`dsh-session-persistence-jsonl`：`<DSH_HOME>/sessions/<projectKey>/<idSegment>/session.vN.jsonl.zstd`

`dsh-api-session-controller` 的客户端封装 `RecordSession.parentSessionId` 承载谱系；`sessions.fork({sessionId, atSeq})` 会立即插入 placeholder 行，所以 fork 出的子会话**立刻可寻址**。

## 四、四个关键设计决策

### 决策 1：删除必须走文件系统，但顺序不能错

DSH 没有删除 RPC，所以唯一路径是 host 侧 fs。生态里的教训：

- **先归档，后移盘**（xohmai）。反过来会在运行期间触发 `host/archived-sessions-changed` 广播，把残留行"复活"到侧栏。
- **不能拿"运行时注册了 Agent"当拒绝条件**——DSH 的 Agent 注册表持有到进程退出，用它判断会导致**永远删不掉**。只拦"确实有活在跑"。
- **附件与派生缓存刻意不删**：`$DSH_HOME/attachments` 与 `$DSH_HOME/cache` 是内容寻址的共享数据。

本插件采用：`归档 → rename 进回收站 → 写 manifest/audit → 清空 project 目录`，并额外做目录归属校验（目录名必须与 sessionId 相符且在 `$DSH_HOME/sessions` 之内）。

### 决策 2：编辑用分叉，不原地改写

`session.v4.jsonl.zstd` 是 **zstd 压缩的单文件**，不是行追加日志。原地编辑需要解压→改写→重压，并重算 `seq` 单调序列。一旦 `seq` 断裂，`session-projection` 缓存、trajectory 投影、`parentSessionId` 谱系全部失效；写入时崩溃即会话报废。

所以本插件的"编辑"= 在该 Turn **之前**分叉 + 把新文本 `prompt` 进子会话。父会话字节级不变。

### 决策 3：消息操作条走 DOM 层，不遮蔽 keyed slot

两条路：

| 方案 | 代价 |
|---|---|
| `priority: -1` 遮蔽 `user` cell，重渲染整个气泡 | 必须复刻 `projectUserText` / `FileTypeIcon` / 附件卡 / 引用摘要；任何版本漂移都会让**用户最常看的那一行**崩掉 |
| DOM 层锚定官方数据属性 | 只依赖 `data-chat-flow-kind` / `data-chat-turn`，原生气泡、Markdown 投影、复制按钮全部保留 |

选后者。锚点都是 DSH 明确输出的属性，**不依赖任何哈希化 CSS-module 类名**（如 `bfNlQW_userRow`），因此不会随构建哈希变化而失效。

副作用：它同时对**所有**用户消息生效，而不是只有最后一条——这正是需求①想要的。

### 决策 4：`inject` 必须为空

这是实测踩到的坑。最初写 `export const inject = ['connection']`，在只组合 `dsh-base` 的 profile 里启动，得到：

```
dsh: warning: 1 entry did not activate
codex-parity (dsh-codex-parity): pending (waiting for service: connection)
```

因为 `connection` 由 **web app 层**提供，不在 `dsh-base` 里。结果是 `apply()` **从未被调用**，插件完全静默、无任何报错。

修复：`inject = []`，在 `apply()` 内 `ctx.get('connection')`，并用 `ctx.inject(['connection'], ...)` 在服务后到时补齐路由。现在日志可见：

```
[dsh-codex-parity] loaded; waiting for the connection service before serving RPC
[dsh-codex-parity] host ready (v0.1.0) with 8 methods: ping, forkAt, promptSession, readTail, trashSession, listTrash, restoreTrash, purgeTrash
```

## 八、已知限制（诚实清单）

1. **编辑仅限最新一条用户消息** —— 与 DSH 原生 `message.branchUnavailable`（"仅可从已完成轮次的最后一条消息分支"）的约束一致。历史消息请用①。
2. **侧边提问面板是纯文本**（`<pre>`），不做 Markdown 高亮。需要完整原生界面请配合 `dsh-side-chat`。
3. **浏览器端渲染未经人工目视验收** —— 主机半段与客户端契约均已自动化验证，且插件已在真实主机激活并服务 RPC；但 UI 的视觉呈现需要重启应用后人工确认一次。
4. **回收站跨卷会失败** —— 会话目录与 `$DSH_HOME` 不在同一卷时 `rename` 报 `EXDEV` 并明确提示，不退化成跨卷复制。
5. **重命名用浏览器原生 `prompt`**，样式不跟随主题。
6. **重启后生效** —— 本机 DSH Desktop 主进程启动于 13:44:11，插件安装于 13:57:01，需重启应用加载。
